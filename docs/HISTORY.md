# Implementation history (formerly ARCHITECTURE.md §16.2–16.5)

Completed-work log, moved out of ARCHITECTURE.md to keep the reference short. Code comments that cite "§16.3" etc. refer to the sections below (numbering preserved). Nothing here is open work except the two items listed in ARCHITECTURE.md §16.

### 16.2 Phase 8's original scope — fully built (0.8.1)

Of the three things phase 8 was scoped to add (§11):

1. **The Summary legend explaining the four everyday cell states** — built. `modReports.DrawLegend`, called from `BuildSummary`, at `O9` down on the Summary sheet.
2. **Conditional formatting for warning (amber fill) and error (red text) states** — built. `modInit.ApplyStatusFormat` gives every location sheet's Status column an amber fill whenever a row reads anything other than `OK` (the "warning state" §5's own column table already called "conditionally formatted"). `modReports.FormatSummaryErrors` gives Summary's Type/Family columns red bold text when a job references a paper stock no longer in `tblPapers` (the `"(not in Papers)"` `IFNA` fallback already in `BuildSummary`'s formula) — the concrete "error state" chosen because it's the one place the workbook's own formulas already flag a genuine data-integrity break rather than a routine per-row nag, and because (like Status) it's pure spilled-formula output with no VBA hook to colour it imperatively. This is a design interpretation, not something the original scoping pinned down beyond the Status column — worth revisiting if a different "error" case turns out to matter more in practice.
3. **Currency from the global setting** — built. `modSettings.CurrencySymbol()` is now read everywhere a money `NumberFormat` or `Format$` previously hardcoded `£` as `ChrW(163)`: `modReports` (Summary and Reports), `modExport`'s export-report snapshot, and `modJobs.RemoveRow`'s delete-confirmation dialog. `modSettings.Money()` — the locale-safe formatter — remains unreferenced by any of these (they build a `NumberFormat`/`Format$` code string rather than a pre-formatted value), and is kept for whenever a future caller needs one.

   **A real Excel quirk surfaced building this, worth knowing before touching any of these sites again:** setting a `Range.NumberFormat` from VBA to a *bare or quoted* currency symbol followed by `#,##0.00` (e.g. `"$#,##0.00"`) is silently canonicalised by Excel to the OS's own regional currency symbol, regardless of what string was actually assigned — verified directly against this workbook over COM (a plain `"$#,##0.00"` round-tripped as `"£#,##0.00"` on this GBP-locale machine). This was invisible for as long as this code hardcoded `£`, because `£` already matched the OS default and needed no canonicalisation; it would have silently defeated `SET_CURRENCY` for any other value the moment this item got wired up naively. The fix: `modSettings.CurrencyFormatCode()` wraps the symbol in Excel's `[$symbol]` locale-currency bracket syntax (no `-LCID` suffix needed), which round-trips exactly as given and was confirmed to render identically to the bare form for the unaffected `£` case — every `NumberFormat` site above calls this rather than `CurrencySymbol()` directly. `modJobs.RemoveRow`'s `Format$` dialog text does **not** have this problem (confirmed separately: VBA's own `Format$` engine does not canonicalise a bare `$`) and keeps calling `CurrencySymbol()` plain — the bug is specific to the `Range.NumberFormat` COM property, not to currency symbols in general.

   **Changing `SET_CURRENCY` still only repaints Summary/Reports on the next `InitialiseWorkbook` run**, same as every other piece of their formatting — `RefreshLocations` does not rebuild them, and that has not changed here.

A large amount of *other* visual/UX work had already been done since phase 8 was originally scoped — the entire 2026-09-21 snag list (freeze panes, tab order, column groups, hide/show toggle, notes wrap, catalogue buttons, Reports layout) — but none of it touched these three specific items until now.

### 16.3 Other loose ends

- **`SET_FOOTER` and `SET_FY_START` — dropped (2026-09-27).** Both were defined names with no code consumer since inception (Report footer, blank; Financial year start, "1 August"). Asked the user whether to wire each up (export footer text / page-print footer for the former, a Reports quick-filter or Summary FY grouping for the latter) or drop them outright — no feature currently needs either, so both were removed: the `tblSettings` rows deleted from `PrintCosts.xlsx` (COM automation on a `%TEMP%` copy, §13.1) along with the two defined names, and `build.ps1`/the full regression suite re-run clean afterwards.
- **`LOC_RollUnit`'s order-dependent conversion gap — fixed (2026-09-27), then superseded in 0.10.11 (2026-10-01).** *The `ConvertQtyIfCentimetres` mechanism and its grey "already converted" shading described below no longer exist. Qty is now held and typed in the sheet's chosen unit, the calculated columns divide a "cm" row's Qty by 100, and `modRegistry.MetresBlock` converts back to metres for `_Data`, so there is no order dependence left to fix. See CHANGELOG 0.10.11. The entry is kept as a record of how the problem was first solved.* The cm→m conversion (`modValidation.OnQtyChanged`) used to only fire on `Qty`'s own edit, so a length typed *before* Paper Stock was chosen was left as raw, un-converted centimetres — on a Centimetres location that meant a job silently stored as 100x too many metres, and nothing in `CheckSheet`/`CheckWorkbook` caught it. Fixed by extracting the conversion into `modValidation.ConvertQtyIfCentimetres`, called from both `OnQtyChanged` (Qty edited — always treats the current value as fresh raw input, same as before) and now also `OnStockChanged` (Paper Stock resolves to a Roll stock — converts a value typed earlier that was left unconverted). `MarkQtyRewritten`'s existing shading is reused as the "already converted" flag so a value `OnQtyChanged` already converted is never divided by 100 twice when Paper Stock changes again afterwards. See `test-rollunit.ps1`.

  **`LOC_RollUnit` is still a per-LOCATION setting, not per-row — noted as a future enhancement, not attempted here.** A location still cannot mix centimetre and metre entry job-by-job; every roll job on a sheet is typed in whichever unit `LOC_RollUnit` currently says. The robust fix for that would be a genuine per-row unit (a real job-row column feeding a calculated `Qty`, a schema bump touching `AddPrintJob`, `RepeatJob`, Export, Import and the job table layout) rather than rewriting the one cell in place. Revisit if mixed-unit entry on a single sheet turns out to matter in practice.
- No calendar-style date picker on the Reports date filters (§8.4) — a confirmed platform limitation on desktop Excel, not a bug, but worth remembering if a future Excel release changes this.
- **Button-lag bug — fixed (2026-09-27), not just mitigated.** A location sheet's buttons used to lag by one click after the cost-columns outline group (§4.1/§9.2) was collapsed or expanded via Excel's own native `+`/`-` control: every location button is `Placement:=xlFreeFloating` (deliberate, see `RelocateButton`'s comment — stops a hide/reveal cycle from corrupting button width), so it no longer auto-tracked the columns under it, and a manual outline toggle is not a macro call, so nothing ran to re-settle it immediately (VBA has no event that fires on an outline collapse/expand). `ThisWorkbook.Workbook_SheetActivate`/`Workbook_SheetSelectionChange` calling `modInit.RepositionLocationButtons` as a proxy only ever mitigated this — a button still sat visibly stale for the brief window right after the click on the outline control itself. **Genuinely fixed by removing the native outline control from this span entirely**, per the tradeoff this entry used to flag as the reason it wasn't done: `modInit.NormalizeJobColumnOutlines` (renamed from `GroupJobColumns`) no longer groups `Paper Cost`→`Disregarded` at all, and a new workbook-wide "Hide/Show cost detail" button (`modInit.ToggleCostColumns`/`ApplyCostColumnsVisibility`, §4.1) toggles that span's visibility instead — an ordinary macro button, so it repositions every affected button in the very same click, with no lag window at all. The native `+`/`-` affordance for this specific column span is gone in exchange; §4.1's occasional-use button list and side-panel button count (now eight) are updated to match. See `test-costcolumns.ps1` (replaces the outline-level assertions `test-groups.ps1`/`test-paid.ps1` used to make for this span).

  **A real bug found immediately after, direct user report: the eighth button visibly overlapped the seventh.** The seven-button side panel (§4.1) had run flush against its available vertical space from the day it was built — seven 22pt buttons plus six 3pt gaps already came within half a point of the full budget between row 1 and the table header — so adding an eighth at the same fixed height literally could not fit, gap or no gap; even packing all eight with zero gap at all was about 3.5pt short of the available room. Growing that space (pushing the header down another row) was rejected as the fix: the panel already starts at row 1 with nowhere to extend upward, and moving the header touches far more of the sheet's layout than this warrants — see this section's own history of layout bugs (the row-scope bug, column drift, button-width corruption) for why that class of change is not made lightly here. Fixed instead by `modInit.SidePanelButtonLayout` (new): derives the side panel's button height and vertical step from whatever room is actually available above the table's current header row, shrinking below the standard 22pt only as far as fitting eight buttons with a real minimum gap (3pt) actually requires, and capping at 22pt so a future rebuild with fewer side-panel buttons looks exactly as it always did. `DrawOneAtTop` gained an optional height parameter to carry this through; `RepositionSidePanelButtons` was updated to call the same function rather than keep its own hardcoded 22, which would otherwise have silently grown every button back to full size — and reopened the overlap — on the very next `InitialiseWorkbook`/`RefreshLocations`/toggle call. **A second bug caught building this fix, worth its own line in §9.2: a first draft declared `SidePanelButtonLayout`'s two new module-level constants next to the function itself, mid-file, rather than in `modInit`'s declarations block at the top — the exact "Variable not defined" compile-hang failure mode §9.2/§13.1 already document from two earlier incidents, hit here despite the comment sitting right above the correct spot warning about it.** Diagnosed the same way those were: `build.ps1` hung with no output, and the stuck Excel process's window title had changed to "Microsoft Visual Basic for Applications" — the blocking compile-error dialog. Fixed by moving both constants up to the declarations block.
- SETUP.md's "What is not built yet" framing has been kept up to date through the 2026-09-21 commits (it correctly describes Import/Export/NextId/Reports-delete as built) — but cross-check it against this document's §16.1/§16.2 rather than assuming either one alone is complete, since they serve different audiences (procedure vs. architecture) and could drift independently.
- **The "Package 10" visual-polish/styling rework — descoped (2026-09-23), not planned.** Earlier drafts of this document forward-referenced an eventual "Package 10" as the home for deferred visual-polish items (e.g. §4.1's clearer reduced-view state indicator). On review, a dedicated styling rework is more than this workbook actually needs — the native Excel formatting already in place (cell-role colours, conditional formatting, the Summary legend, §16.2) is considered sufficient, and no further styling package is currently planned. Individual small polish ideas (like the reduced-view indicator) stay noted where they arise, but are no longer tracked toward a bundled future package.
- **User-facing design customisation — a speculative "maybe someday" idea, not a plan.** Letting users adjust the workbook's own visual presentation themselves (colours, branding, etc.) is worth a passing mention as a possible future direction if a real need for it turns up, but is explicitly not scoped, designed or committed to — noted here only so it isn't reinvented from scratch if it ever comes up again.
- **Customisable row height — a speculative "maybe someday" idea, not a plan (2026-09-27).** Direct user feedback while testing Repeat Job: the current fixed row height reads as a touch cramped, and a "spaced out" look is preferred, but Repeat Job's own note text was deliberately kept to one line (above) rather than solving this by letting a note wrap taller - a single row growing to fit its own content is not the same as every row being a bit taller by choice. If this turns out to matter in practice, it belongs as a genuine user-facing setting (e.g. a location- or workbook-level row height), not a side effect of whatever text happens to be longest that day. Not scoped or designed beyond this note.
- **Automate "add a print room" — direct user feedback (2026-09-27), built.** The documented procedure (§4.4) was manual and multi-step (copy sheet, rename tab, Clear All, Clear defaults, re-enter room name/department/defaults, Select printers…, Refresh Locations) — enough steps that skipping one was easy, and a copied sheet always started life carrying whatever the source sheet happened to contain until every clear step ran. Built as a "Add print room..." button at the bottom of the Settings sheet (§4.4's own addendum has the implementation detail — `modRegistry.AddPrintRoom`/`CreatePrintRoom`), which performs the whole sequence and goes further than the manual version ever did in guaranteeing a genuine fresh start. Every existing manual route (§4.4, and manual sheet deletion) stays untouched and fully functional alongside it.
- **Automate "remove a print room" — direct user feedback (2026-09-27), built.** The counterpart to the item above, and the open question it deliberately left unanswered: a "Remove print room..." button next to "Add print room..." (§4.3's addendum has the implementation detail — `modRegistry.RemovePrintRoom`/`DeletePrintRoom`). §4.3's export-based mitigation already covered the "sheet deleted by accident" recovery story; this is the *deliberate*, in-app counterpart — pick a room, refuse outright if it's the last one left, name what will be lost (record count, date span, export status) with an extra warning when there are unexported changes, then require the room's name typed back exactly before anything is deleted. The manual route (right-click the tab → *Delete*) is untouched.
- **Settings-page button arrangement — revisited, not yet a full pass.** §16.3 previously flagged the growing pile of per-location and per-sheet buttons (§4.1's toolbar/side-panel work, the Settings-page additions above) as worth a dedicated look once things settled. "Remove print room..." landing right next to "Add print room..." (same row, not a new one) is a small step in that direction — placing a new button beside its natural counterpart rather than picking its own spot in isolation — but a genuine overall-arrangement pass across every sheet's buttons is still not done.

See §7.2's rewrite for the full design. `modLists.UNAVAILABLE_SUFFIX` (new), `MarkStocks`/`MarkPrinters` (new — append the suffix to whichever items in the FULL permitted/active list the other field's current value rules out), `CleanPick` (new, `Public` — strips it back off), `BindStockRange`/`BindPrinterRange` (now always stage the full list, marked, while still computing the narrowed/compatible list purely to feed the unchanged `AutoFillIfSingle`). `modValidation.Clean` (new, private) calls `CleanPick` on a Printer/Paper Stock cell (table row or default cell) the moment it changes, before any compatibility check runs, so a marked selection is stripped back to a real catalogue name and falls straight into the SAME AT-05 handling 0.9.0 already built — no new incompatibility-handling logic, just a new way to reach the existing one. `test-dropdowns.ps1` updated: the old assertion that a narrowed staged list contained *only* the compatible printers is replaced with an assertion that it contains *all* permitted printers, the incompatible one marked; a new case picks the marked entry directly and checks the marker is stripped and AT-05 still fires. Auto-fill-when-one-option assertions (r1/r2/r4) are untouched and still pass, because auto-fill was deliberately kept on the narrowed list rather than switched to the marked one.

**Why this is flagged, not just shipped:** what was actually asked for was real per-item visual styling — italics, a lighter colour, background shading on the unavailable entries. A native Excel Data Validation dropdown cannot do that; the list is rendered by Excel with no per-item formatting hook exposed to VBA. A text suffix is the closest approximation reachable without replacing the in-cell dropdown itself with a worksheet-based picker (§9.3's `_Picker` sheet already proves that pattern works for the two multi-select fields, and unlike a native dropdown, a real worksheet CAN render genuinely muted/greyed cells per item). That larger change — trading a familiar in-cell dropdown arrow for a click-to-open mini-dialog on two of the table's busiest columns — was weighed and deliberately not taken this round; the user chose the smaller, native-dropdown-preserving option when asked. Revisit if the text marker proves unclear in practice; the worksheet-picker approach above is the documented fallback.

**Addendum (0.9.12, 2026-09-23) — Settings-page layout: About block removed, its space given to the action buttons — built.** Also user feedback on already-shipped behaviour, not a Package item. The on-sheet About block (`modVersion.WriteAbout`, now deleted along with its private `Lbl` helper) duplicated the About button's own popup for no real benefit while permanently occupying several rows at the foot of the Settings sheet. `modVersion.ShowAbout` now carries the brief description that used to live only in the block's prose, so nothing the block showed is lost. The eight action buttons that used to run down column T (`Refresh Locations`, `Check workbook`, `Re-stamp prices...`, `About`, `Export All Locations...`, `Import (choose room)...`, `Backup workbook...`, `Restore workbook...`) move into the freed space instead, in two rows of four: everyday workbook actions first, then the data-movement actions. `modInit.TablesBottom` (new, `Private`) finds the row below whichever `ListObject` on the sheet runs deepest — the same calculation `WriteAbout` used to do inline before clearing its own text — and both the button rows and a clear of the old About block's former text area (a workbook built before this change loses the stale prose the next time setup runs on it, not just on a from-scratch rebuild) are anchored to it. No dedicated test script: the change is layout-only, with no new logic beyond a row/column arithmetic helper already exercised by every `InitialiseWorkbook` run in the regression suite.

**Addendum (0.9.15, 2026-09-25) — job-table Data Validation corruption fixed, direct user report.** Not numbered as a Package: a bug report ("every column from G to Q shows a dropdown to pick a technician, and picking one overwrites the cell"), not a snag-list item. Confirmed against the built `.xlsm` over COM (not just reasoned through): every column from Unit through Chargeable Cost carried the Technician list (`=lstTechnicians`) as its `Formula1`, and Student Name/Student No both carried the Date/Time rule.

**Root cause: `modInit.ReorderJobColumns` (0.9.4) reorders columns via repeated `Range.Cut` + `Range.Insert Shift:=xlToRight` inside the table.** Excel extends a validated column's rule onto cells newly shifted in beside it on each `Insert`, and the ~30 inserts one full reorder performs compound that into a wide, wrong span. The corruption happened once — when 0.9.4 first reordered an already-populated workbook's columns — and then sat there undisturbed, since `ReorderJobColumns`'s own "already in the right position" check means a column whose name is already correctly placed is never cut and re-inserted again, so it never got a second chance to un-corrupt itself. Nothing before now ever cleared or re-asserted validation on the columns this landed on (Unit, Area m2 and the cost columns are calculated and were never expected to carry any; Student Name/No never had any either) — only Technician/Printer/Paper Stock, which `modLists.BindColumns` already overwrites unconditionally on every run, self-healed on their own.

**Fix: `modInit.EnsureJobColumnValidation` (new)**, called from `modLists.BindColumns` right before it rebinds Technician/Printer/Paper Stock. Clears the whole job table body's validation, then restores exactly what `PrintCosts.xlsx` ships for Date/Time (date, on/after 01/01/2000), Qty and Print Width mm (decimal, greater than zero), Disregard Paper/Disregard Consumable (Yes/No), and Paid (Yes/No, `modInit.EnsurePaidColumn`'s own values). Because `BindColumns` is already the "rebuild dependent dropdowns, self-heal, never trust what a previous run left behind" entry point every setup run, **Refresh Locations**, **Check workbook**/**Check this sheet** and the multi-select picker all go through, this reaches an already-corrupted workbook the next time any of those run — a full rebuild via `build.ps1` is not required, though one was done to verify the fix (rebuilt `src\PrintCosts.xlsm`, re-inspected both location sheets' validation over COM, confirmed all five existing job rows' data and cost formulas were untouched by the clear/reapply).

**Not fixed at its own root** — `ReorderJobColumns`'s Cut+Insert still corrupts validation the same way, in principle, the next time it actually has to move a column (a genuinely new job-row column requiring a further reorder). `EnsureJobColumnValidation` running immediately after every time makes that moot in practice, since nothing downstream ever sees the corrupted state, but a future column addition that needs `ReorderJobColumns` to move things again is worth re-checking against this note rather than assuming it can't recur.

**Addendum (2026-09-26) — down to one shipped location sheet; sample data rewritten for feature coverage, user request.** `PrintCosts.xlsx` shipped two location sheets, Example Print Room and Annexe, since the earliest phases. With the documented add-a-location procedure being "duplicate an existing sheet, rename it, Clear All" (§4.4), a second pre-built sheet added nothing a new user couldn't get from the first by that same procedure, and risked the opposite: which one is the "real" template, are the two linked, does deleting one break anything. Annexe (and its `tblJobs_ANNEX` table, `LOC_*` sheet-scoped names, and single sample row) was deleted outright from `PrintCosts.xlsx` — safe by construction, since `_Registry`/`_Data`/Reports/Summary are all rebuilt from whatever location sheets are actually present the next time `InitialiseWorkbook`/`RefreshLocations` runs (§4.2), not hand-maintained against a fixed sheet count. Verified: `build.ps1` reports "1 print room registered," `_Data` spills exactly the surviving sheet's rows, and every button re-points correctly.

Example Print Room's twelve sample rows (`UNI-MAIN-00001`–`00012`, up from five) were rewritten to exercise the full feature set in one place rather than splitting coverage across the sheet that got removed: every paper stock (all four Sheet-family standard sizes, the one Custom-sheet offcut, and all four roll widths, §3.3), every printer (all three consumable types plus Latex, which previously only Annexe was permitted to use — added to Main's `LOC_Printers`/`AM7` accordingly), every technician, both `Disregard Paper` and `Disregard Consumable` individually (previously only Paper had a sample), a roll job at full stock width vs. an explicit narrower `Print Width mm` vs. one deliberately wider than the stock (still the invalid row, now `UNI-MAIN-00012`, kept last by both date and Job ID as before), and the three student-identification shapes D1/D19 actually accept: name and number both given, number only, and a department name in Student Name with no number (the free-text "charge to a department" convention, §2 D19). Not attempted: a sample demonstrating the AT-11 name/number consistency warning (§6.1, `modValidation.CheckStudent`) — that check fires as a live entry-time message box, not anything persisted to the Status column or any cell, so a static sample row claiming to demonstrate it would just look like an ordinary valid row with a misleading Notes comment.

Edited via Excel COM automation on a `%TEMP%` copy, never opening `PrintCosts.xlsx` directly, for the same OneDrive/AutoSave reason `build.ps1` never does either (§13.1) — confirmed the hard way mid-task, when a throwaway diagnostic that opened the live file directly (to chase an unrelated PowerShell/COM bug, next paragraph) had its test values committed to the tracked file by AutoSave despite closing with `SaveChanges:=False`, recovered via `git checkout`.

**PowerShell/COM gotcha worth recording alongside §13.2's existing ones: a shared function that sets `Range.Value2` gets `InvalidCastException` the second time it's called with a different argument type at that same call site.** Writing many typed cell values through one `SetCell($lo, $colName, $rowIdx, $value)` helper — `$cell.Value2 = $value` — worked for the first assignment (a `[DateTime]`, converted to an OLE Automation date first) and threw `Specified cast is not valid` on the very next call with a plain string, even though either assignment succeeds fine in isolation or written out inline. PowerShell 5.1's DLR caches the dynamic dispatch for a COM property setter per call site rather than per argument type; a shared helper invoked with varying argument types across a loop is exactly the shape that trips it. Fixed by dropping the dynamic `.Value2 =` syntax in favour of late-bound reflection, which has no such cache: `$cell.GetType().InvokeMember('Value2', [Reflection.BindingFlags]::SetProperty, $null, $cell, @($value))`.

### 16.5 Printer/paper compatibility rework (0.10.0, 2026-09-28) — built

Direct user request, from real-world testing: the family-based compatibility model was too coarse. `tblPaperFamilies` was standing in for roll-width bands (`Short Roll` ≤24in, `Long Roll` >24in), so a printer opting into `Long Roll` accepted *any* roll stock from 914mm to 1370mm+ with no real width check, and a printer opting into `Sheet` accepted any sheet size at all, A4 up to A0, with no size check either. Two requirements, delivered together as one phased-but-single-session change (see the approved plan for the original phase breakdown; phases 1–3 landed as one build/verify cycle rather than separately, since each was too small on its own to verify in isolation against real Excel behaviour).

**Requirement 1 — capacity-based compatibility, replacing family membership.**

- `tblPrinters` gains **Max roll width mm** (numeric) and **Max sheet size** (a Standard Sizes pick) in place of the old `Supported families` multi-select — a printer takes roll stock iff the first is set, sheet stock iff the second is set, both can be set on the same printer (`modCatalog.EnsurePrinterCapacityColumns`).
- `modCatalog.Compatible` is a real size fit now: `stock.WidthMM <= printer.MaxRollWidthMM` for roll, `FitsWithinMaxSheet` (either orientation, so a sheet can be fed either way round) for sheet. `clsPrinterDef.Families` is gone; `modPicker.PickFamilies` and the Printers-sheet "Select families..." button are removed outright (`modMain.btnSelectFamilies` too) — a printer's capability is fully described by the two numeric fields, nothing left to multi-select.
- `modCatalog.MigratePrinterCapacities` is the one-time, idempotent migration: for each printer, it derives Max roll width mm as the widest Roll-family stock the *old* family-list rule already let it take, and Max sheet size as the smallest catalogue Standard Size whose bounding box (either orientation) contains every Sheet-family stock it already took — a principled translation of the old semantics into the new model, not a guess, so upgrading a workbook doesn't silently change what any printer can already do. Must run before the family merge below, while `tblPapers`' Family values still say `Short Roll`/`Long Roll` and can still be matched against the legacy `Supported families` text; removes that legacy column itself once every printer has been read, which is what makes the whole migration a true one-off (the next `InitialiseWorkbook` run exits immediately on the missing column).
- `modCatalog.MigrateRollFamilies` merges `Short Roll`/`Long Roll` into a single `Roll` family, since families only need to distinguish Sheet from Roll now (§3.1). `Family` and `Measure` stay two separate columns regardless — `Measure` remains the only thing formulas key off (I2), and `Family` is now purely a grouping/reporting label; the "family and measure look like the same thing" duplication the request flagged is resolved by Printers no longer referencing family at all, not by collapsing the columns. The `Family` → "Paper Format" rename floated during planning was **deliberately not done** — every `CellIn`/`ColIdx` call site and `modBackup.CatalogKeyHeader` reference it by that name, and the rename bought nothing once Printers stopped depending on it; a pure cosmetic simplification, safely deferrable.

**Requirement 2 — "Supplied by student" paper stock**, for when a student brings their own paper.

- Two ordinary `tblPapers` rows, not synthetic in-memory stock — `Supplied (Roll)`/`Supplied (Sheet)`, `Cost = 0`, Width/Height mm blank (`modCatalog.EnsureSuppliedByStudentColumn`, a new `Supplied by student` Yes/No column). Being real catalogue rows is what let every existing Reports/Summary Family/Type/Unit lookup and the dropdown-staging path handle them with zero further code — `modCatalog.Compatible` is the one place that needs to know a stock is one of these (`clsStock.SuppliedByStudent`), skipping the size-fit check since there isn't a size until job entry.
- `S_UnitCost = 0` for both rows means `Paper Cost` computes to zero automatically (§5.1's `ROUND(Qty * 0, dp)`) — **no cost formula was touched**. Consumable Cost is unaffected (still `Area × S_ConsRate` from the printer), so ink is charged normally and can still be waived per row via the existing Disregard Consumable flag, exactly as asked.
- The real size is entered per job: `Print Width mm` becomes *required* (not optional) for `Supplied (Roll)`, and the new **Sheet size** job-row column (§5, schema 1.1 → 1.2) plays the same role for `Supplied (Sheet)` — both validated against the *chosen printer's* capacity (`modValidation.OnWidthChanged`/`OnSheetSizeChanged`), and re-validated if the printer changes afterward on an already-sized row (`RevalidateSuppliedSize` — the same order-dependency class of bug §16.3 already fixed once for `LOC_RollUnit`/centimetres, applied here pre-emptively rather than found the hard way). A blank required value is caught by `H_Issues`/Status (`modInit.EnsureJobIssuesFormula`) the same way every other required field already is.
- The two rows are kept at the bottom of the Paper Stock dropdown by construction, not a sort tie-break: `modLists`' stock-staging routine preserves `tblPapers` row order, and `EnsureSuppliedByStudentColumn` always appends via a bare `ListRows.Add` (no `Position` argument).

**Two real bugs found building this, both worth remembering for future VBA work:**

1. **`Range.Formula` (not `.Formula2`) is capped well under the length `EnsureJobIssuesFormula`'s new H_Issues clauses needed**, raising a bare 1004 ("Application-defined or object-defined error") with no length-related message. Same limit `EnsurePrintersDisplay`'s own `B7` formula already worked around (§4.1) — `.Formula2` has no such cap. Found by bisecting the formula clause-by-clause via a temporary VBA test Sub until the exact failing assignment was isolated, since the error itself gives no hint it's about length.
2. **An object's public field passed as a `ByRef` output parameter doesn't reliably write back over COM.** `modCatalog.LoadCatalog` called `StdSizeDims(p.MaxSheetSize, p.MaxSheetWidthMM, p.MaxSheetHeightMM)` directly against `clsPrinterDef`'s own fields — `StdSizeDims` returned `True` with the correct values every time, but `p.MaxSheetWidthMM`/`MaxSheetHeightMM` stayed `0` regardless, silently breaking every sheet-stock compatibility check (a printer with a correctly-migrated `Max sheet size` name rejected every real stock, while `Supplied (Sheet)` — which skips the size check — still worked, which is what made this look at first like a migration bug rather than a ByRef one). Fixed by routing through plain local `Double` scratch variables and assigning the class fields afterward; the other `StdSizeDims` call sites (`modSnapshot.StampRow`, `modValidation`) already used local variables and were unaffected.

**A third issue, in the test harness rather than the product: `EnsureJobIssuesFormula` running unconditionally on every `BindColumns` call (setup, Refresh Locations, Check workbook/sheet, the picker) made an already-marginal COM timing race worse.** Rewriting a ~1.5KB formula across a whole table column on every one of those calls — most of which previously did nothing to `H_Issues` at all — occasionally left Excel still settling a recalculation when the next COM call landed, intermittently raising `RPC_E_CALL_REJECTED` ("Call was rejected by callee") in `test-import.ps1`, right after `ApplyImportConfirmed`'s own Check-sheet sweep. Fixed two ways: `EnsureJobIssuesFormula` is now checked-first (compares the target formula against the first cell's current one, skipping the write entirely when nothing would change — the common case after the first run), and `test-import.ps1` now waits on `TestCommon.ps1`'s `Invoke-ComRetry` (previously only used right after `Workbooks.Open`, generalised in its own comment to cover this second site) rather than assuming `CalculateFullRebuild` always returns settled.

**A structural side effect worth flagging for the next person who adds a job-row column: inserting one shifts every later column through a cut+insert cycle the next time `ReorderJobColumns` runs, and `.Hidden`/`OutlineLevel` don't reliably travel with that shift any more than the validation ranges and widths §5's own note already warns about.** Adding the Sheet size column left `S_StampedBy` (and the rest of the snapshot block) visibly un-hidden, and `Job ID` picked up a stray outline level 2 — both caught by `test-groups.ps1`, neither near the column that actually moved. Fixed by two small, unconditional reassertions in `modInit.NormalizeJobColumnOutlines` (`ReassertSnapshotHidden`, and a explicit `OutlineLevel = 1` on `Sheet size`/`Status`/`Job ID`) rather than trusting Cut+Insert to have preserved them — the same "restore what Cut+Insert can silently disturb" idiom `EnsureJobColumnValidation`/`ApplyJobColumnWidths` already apply to validation and widths, now extended to `.Hidden`/`OutlineLevel` too.

Verified by the full existing regression suite (all green; `test-dropdowns.ps1` and `test-paid.ps1` updated for the new capacity-based compatibility model and the schema bump respectively, `test-import.ps1` fixed for the COM-timing issue above) plus new `test-suppliedstock.ps1`: zero Paper Cost with normal Consumable Cost for both roll and sheet, required-field enforcement, rejection when an entered width/size exceeds the chosen printer's capacity (roll and sheet), and Disregard Consumable still waiving ink cost on a supplied-stock row.
